将人员管理方式转为员工身份、生命周期与组织展示规则。

## 业务问题

客户以员工编号管理人员，前期系统设计存在另外一层账号。客户希望登录与人员管理保持一致。同时，组织名单需要体现领导岗位与职务层级，不能简单按编号排列全部人员。

如果只把“统一登录”和“领导排前面”交给开发，入职、离职、返聘、编号复用和组织展示等条件仍然不清楚。我需要把这些管理要求拆成双方可以讨论与确认的业务规则。

## 我的判断与处理

我与客户和开发从可操作性、唯一性及现有管理方式讨论账号设计，推动以员工编号登录；将新入职递编、离职停用、同一人员返聘恢复原编号等情况单独说明。

另一个判断是：身份标识与名单排序承担不同用途。编号用于识别员工，组织列表先体现岗位层级，同层级再按编号排序，避免让领导顺序被编号固定。

## 实际结果与版本说明

本人确认已调整并使用员工编号登录，领导与普通员工按约定规则展示。资料中2024年出现过身份证号后8位登录的变更要求；本人于2026年10月8日确认该要求没有实施，最终仍使用员工编号。

2022年登录需求文件早于我加入公司；2023年3—5月属于前期材料梳理阶段。这些文件说明项目背景，不代表我从零创建了全部需求，也不能单凭文件日期证明个人贡献。

## 证据边界

原件可支持项目存在登录、排序、需求变更与验收归档过程。返聘恢复原编号及最终登录方式主要依据本人确认；本次未独立登录客户系统复验，也未核实每份验收件的签署状态。不使用虚构效率、用户人数或零故障数据。
